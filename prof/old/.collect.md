# Performance Metrics Reference

## Collection Methods

| Tool | Source | Covers |
|------|--------|--------|
| **load tester** (`bench_v2`) | External binary (client side) | Throughput, E2E latency, error rate |
| **engine instrumentation** | Tracing spans + gauges in `Engine` | Ingestion rate, flush rate, queue wait, batch size, compaction duration |
| **HdrHistogram** | Stats library (embedded) | Server-side latency percentiles (WAL, queue, compaction) |
| **tokio-console** | External CLI tool | Async task states (polling, idle, blocked on channel) |
| **pprof / perf + inferno** | External profiling tools | CPU hotspots, kernel-level syscall breakdown |
| **`/proc` / `ps` / `iostat`** | External binaries | CPU %, RSS memory, disk I/O |

---

## Metrics & Targets

### CPU Utilization (% of 1 core)
Where: external binary (procfs / `top` / `perf stat`)

Engine is single-threaded (actor model). One core maxed = 100%.

| Rating | Range | Context |
|--------|-------|---------|
| Good | < 60% | Has headroom for spikes |
| Great | < 30% | Well under capacity |
| Exceptional | < 10% | Barely breaking a sweat |
| Bad | > 90% | Saturating the engine — queuing will spike |

---

### Memory (RSS, MB)
Where: external binary (procfs or `ps -o rss`)

Should be predictable regardless of throughput (bounded memtable + fixed SSTable cache).

| Rating | Range | Context |
|--------|-------|---------|
| Good | < 200 MB | Reasonable for a data service |
| Great | < 100 MB | Tight, fits anywhere |
| Exceptional | < 50 MB | Minimal footprint |
| Bad | > 500 MB | Leak or unbounded growth |

---

### Disk I/O Latency — WAL Append (P99, µs)
Where: **server metrics** → engine instrumentation (time the WAL `append` call)

Sequential write + sync. Dominated by `fsync`.

| Rating | Range | Context |
|--------|-------|---------|
| Good | < 500 µs | Typical SSD with `fsync` |
| Great | < 100 µs | NVMe / batching amortizes sync |
| Exceptional | < 10 µs | O_DIRECT + polling, or no fsync per-write |
| Bad | > 2 ms | Spinning disk or OS under pressure |

---

### Disk I/O Throughput (MB/s written)
Where: external binary (`iostat -x 1`)

WAL + SSTable flushes + compaction. High throughput = too many flushes (small memtable).

| Rating | Range | Context |
|--------|-------|---------|
| Good | < 50 MB/s | Healthy for a single process |
| Great | < 20 MB/s | Efficient write pattern |
| Exceptional | < 5 MB/s | Minimal write amplification |
| Bad | > 100 MB/s | Too many flushes, compaction falling behind |

---

### Ingestion Rate (records/s)
Where: **server metrics** → counter in `Engine::batch_insert` / `Insert` handler

Records processed by the engine per second (not client-sent — client may outpace engine).

| Rating | Range | Context |
|--------|-------|---------|
| Good | > 10,000 rec/s | Single-threaded, batch commit |
| Great | > 50,000 rec/s | Tuned batching, mmap WAL |
| Exceptional | > 200,000 rec/s | Lock-free memtable, no fsync per-batch |
| Bad | < 1,000 rec/s | Per-record overhead dominates |

---

### Flush Rate (flushes/s)
Where: **server metrics** → counter each time memtable flushes to SSTable

Memtable → SSTable flushes. High rate = small memtable or high throughput.

| Rating | Range | Context |
|--------|-------|---------|
| Good | < 0.2 /s (≤1 per 5s) | Healthy, amortized |
| Great | < 0.1 /s (≤1 per 10s) | Large memtable, low write amplification |
| Exceptional | < 0.05 /s (≤1 per 20s) | Near-idle flush cycle |
| Bad | ≥ 1 /s | Memtable too small, or throughput too high for memtable size |

---

### Queue Wait Time (P99, µs)
Where: **server metrics** → engine instrumentation (time from command received in channel to processing starts)

Time a command waits in the mpsc channel before the engine processes it.

| Rating | Range | Context |
|--------|-------|---------|
| Good | < 1,000 µs | Acceptable queuing |
| Great | < 100 µs | Engine keeps up easily |
| Exceptional | < 10 µs | Near-zero contention |
| Bad | > 10,000 µs | Engine saturated — range query blocking everything |

---

### Recv Batch Size (avg records per engine poll)
Where: **server metrics** → engine instrumentation (count how many `recv_many` returns per iteration)

How many commands `recv_many` collects per call. Higher = better amortization.

| Rating | Range | Context |
|--------|-------|---------|
| Good | > 32 | Decent batching |
| Great | > 128 | Good WAL amortization |
| Exceptional | > 512 | Near-max throughput |
| Bad | < 8 | Not enough concurrent load |

---

### Compaction Duration (P99, ms)
Where: **server metrics** → engine instrumentation or HdrHistogram (time the `compact()` call)

Time to merge N SSTables into 1. Spikes affect concurrent range queries.

| Rating | Range | Context |
|--------|-------|---------|
| Good | < 200 ms | Minimal impact |
| Great | < 50 ms | Fast read + sort |
| Exceptional | < 10 ms | Tiny SSTables |
| Bad | > 1,000 ms | Range queries will stall |

---

### End-to-End Latency — Insert (P99, µs)
Where: **load tester** (`bench_v2` records per-insert round-trip time)

Client sends → server decodes → engine processes → WAL flush → ack.

| Rating | Range | Context |
|--------|-------|---------|
| Good | < 10,000 µs (10ms) | Acceptable for log ingestion |
| Great | < 1,000 µs (1ms) | Near real-time |
| Exceptional | < 100 µs | In-memory only, no fsync |
| Bad | > 50,000 µs | Engine queuing or WAL sync bottlenecks |

---

### End-to-End Latency — Range (P99, µs)
Where: **load tester** (`bench_v2` records per-range round-trip time)

Client sends query → server → engine spawns scan → records stream back → client receives all.

| Rating | Range | Context |
|--------|-------|---------|
| Good | < 50,000 µs (50ms) | Acceptable for log querying |
| Great | < 10,000 µs (10ms) | Fast scans without merging much |
| Exceptional | < 1,000 µs (1ms) | Index-only lookup, minimal records |
| Bad | > 200,000 µs | Too many SSTables or per-record overhead |

---

### Error Rate (%)
Where: **load tester** (`bench_v2` tracks failed inserts + ranges)

Failed operations / total operations × 100.

| Rating | Range | Context |
|--------|-------|---------|
| Good | < 0.1% | Occasional connection drops |
| Great | < 0.01% | Rare |
| Exceptional | 0% | Perfect |
| Bad | > 1% | Systematic failure |

---

## Which Tool For Which Bottleneck

| Bottleneck | Tool | What to look for |
|-----------|------|------------------|
| **CPU-hot engine loop** | `pprof` / `perf` flamegraph | Wide `MergeIter::next`, `BTreeMap::insert`, `sort_by` bars |
| **Async task blocked on channel** | `tokio-console` | `engine_loop` task in "polling" or "idle" for too long |
| **Per-record mpsc handshake** | Engine instrumentation | Time gaps between server send and engine recv |
| **WAL fsync latency** | Engine instrumentation + HdrHistogram | P99 WAL append time > 1ms |
| **Compaction pressure** | Engine instrumentation | Compaction overlapping with range queries |
| **Memory leak** | `/proc` RSS tracking | RSS growing unbounded over hours-long benchmark |
